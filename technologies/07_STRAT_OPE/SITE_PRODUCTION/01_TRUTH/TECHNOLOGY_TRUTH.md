## 1. Definition
**SOURCE CONFIRMED.** проSTRAнство is an expert system that formalizes a management problem as a problem unit / Problem Unit, uses confirmed triggers to select the required strategic frameworks, connects the strategic output through a bridge / Bridge with a limited set of operational instruments, owners and metrics, and tests the assembled contour in a Sprint 30-60-90.

Primary source: proSTRANSTVO_Операционная_Система_v1.0.docx §1. Cross-check: Evidence Matrix v1.0; Artifact & Transition Register v1.0; current commercial presentation extraction.

## 2. Audience / decision-maker
**SOURCE CONFIRMED.**
Primary decision audience: owner, CEO/general director, client sponsor and first management circle. Product documents also identify functional owners involved in the affected contour.
The technology is not entered merely because a person is interested in methodology: paid Diagnostics requires management pain, mandate, access to data/facts and readiness to accept an adverse verdict.

Sources: Diagnostics Client v0.3; Qualification Before Diagnostics v1.0; FAQ v1.0.

## 3. Object of work
**SOURCE CONFIRMED.**
The object is the client’s management contour around a concrete problem: what exists, what works, what is broken, what should not be touched, and what should be rebuilt. A symptom is not accepted as the object of intervention until it is converted into a Problem Unit supported by facts, result impact, owner/mandate, contour and triggers.

Sources: Operating System v1.0 §§2,4,6; Evidence Matrix sheets 01/02.

## 4. Job / problem addressed
**SOURCE CONFIRMED.**
The technology addresses management situations where a complaint or symptom must be converted into a verified problem, the field of strategic choices must be narrowed, and a selected strategic output must be connected to executable operational carriers rather than ending as a list of ideas or an untested session result.
It explicitly protects against continuing work when facts, mandate, owners, data or an object of further work are absent.

Sources: Operating System v1.0 §§2,4,8,11,12; Qualification v1.0.

## 5. Mechanism
**SOURCE CONFIRMED.**
Core mechanism:
1. capture complaint/symptoms without treating them as diagnosis;
2. formalize Problem Unit;
3. diagnose the current contour;
4. confirm and rank triggers;
5. group 1–3 related triggers per Session;
6. select a constrained strategic working set;
7. build Bridge from strategic output to operational instrument, owner, metric, rhythm and Sprint artifact;
8. launch no more than 3–5 instruments in Sprint 30-60-90;
9. evaluate the active contour and either continue, rebuild, transfer or exit.

Sources: Operating System v1.0 §2; Artifact Register sheet 04.

## 6. Inputs / data
**SOURCE CONFIRMED.**
Inputs can include management complaint, interviews, documents, reports, accounting/management systems, metrics, decisions, meeting evidence, data extracts, mandate/right to inspect the contour, named owners and constraints.
Evidence strength matters; opinion alone is not enough for a transition verdict.

Sources: Operating System v1.0 §§2–5; Diagnostics v0.3; Evidence Matrix sheet 01.

## 7. Core algorithm / cycle
**SOURCE CONFIRMED.**
Problem/symptom → Problem Unit → contour diagnosis → triggers → Session grouping → strategic working set → operational working set → Bridge → Sprint charter → baseline + decision log + 30/60/90 control → Sprint verdict → Support only when an active object exists.
Return loops are allowed: Session can return to Diagnostics; Sprint can return to Session/Bridge; Support can open a new Sprint/rebuild. Transition is evidence-gated, not calendar-gated.

Sources: Operating System v1.0 §§2,7–11; Artifact Register sheets 02/04.

## 8. Outputs / statuses
**SOURCE CONFIRMED.**
Diagnostics current P1B verdicts:
- запускать / Go — 15–18;
- запускать с условиями / Conditional Go — 12–14;
- удержать / Hold — 7–11;
- остановить / Stop — 0–6.
Six criteria are scored 0–3: facts/data, problem severity, mandate, owners, contour state, readiness for next stage.

Other stages have their own decisions:
- Session: launch Sprint / Hold / return to Diagnostics / Stop;
- Sprint: scale / continue / rebuild / stop / transfer;
- Support: continue / reduce participation / new Sprint / rebuild / exit.

Sources: Operating System v1.0 §§3,5; Evidence Matrix sheet 03.
Conflict note: older v0.3 client/commercial materials contain superseded diagnostic mathematics or three-status shorthand. See C-001/C-002.

## 9. Roles / responsibilities
**SOURCE CONFIRMED.**
Roles appearing in the current operating/product corpus include: Diagnostics conductor, Session conductor, Sprint owner, Support owner, methodologist, evidence archivist, critic, management sponsor, functional owners, metric/data owner, financial owner, client owner and IT owner.
The technology does not replace client owners; absence of owner/mandate is a transition constraint or stop condition.

Sources: Evidence Matrix sheet 01; Artifact Register sheet 01; Sprint/Support client v0.3.

## 10. Products
**SOURCE CONFIRMED.**
1. **Диагностика** — mandatory paid entry; verifies problem, contour, evidence and readiness; may legitimately end without Session.
2. **Сессия** — accepts a confirmed diagnosis, narrows choice, assembles strategic/operational working set, Bridge and Sprint charter.
3. **Спринт 30-60-90** — tests the selected contour in action with owners, baseline, rhythm, metrics and decision log.
4. **Сопровождение** — checks sustainability of an active contour after Sprint; cannot be sold when no such object exists.

Sources: Operating System v1.0 §§3–4,8–10; four product folders; FAQ v1.0.

## 13. Evidence
**SOURCE CONFIRMED.**
Evidence is structured as checked conclusion → fact → source → artifact → verification owner → score/impact → stop-line.
A formally existing report, process, metric, owner or meeting is not proof that the element works. “Works” requires linkage to management decision/action through owner, rhythm and metric.

Source: Evidence Matrix v1.0 sheets 01/02.

Cases: the corpus contains 12 generalized management examples. The catalog explicitly states they are generalized examples, not descriptions of specific companies. Therefore they are illustrative evidence, not named-client outcome proof.

## 14. Boundaries / anti-category
**SOURCE CONFIRMED.**
проSTRAнство must not be represented as:
- a catalog/menu of strategic frameworks or tools;
- an ordinary strategic session;
- a free audit/report;
- a client project office;
- a training product;
- a guaranteed-result 90-day implementation promise.

Operational boundaries:
- Diagnostics is the mandatory paid entry;
- Session is not automatic after Diagnostics;
- no Sprint without Bridge;
- no more than 3–5 instruments launched in one Sprint;
- no Support without an active post-Sprint object;
- no changing the core merely for sales/design clarity;
- no English-first public terminology;
- no separate AI function.

Sources: Operating System v1.0 §12; FAQ v1.0; Language Standard v1.0; visualization semantic QA.
