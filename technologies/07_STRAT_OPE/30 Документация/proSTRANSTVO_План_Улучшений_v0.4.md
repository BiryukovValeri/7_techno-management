# проSTRAнство. План улучшений документации v0.4

Дата фиксации: 15 июля 2026  
Статус: план следующей версии  
Формат: внутренний рабочий документ

## 1. Главный вывод

Комплект документации и кейсов по технологии проSTRAнство собран и может считаться рабочей базой.

В составе уже есть:

- методология технологии;
- этапы Диагностика -> Сессия -> Спринт -> Сопровождение;
- инструментальное ядро 115;
- стратегические модели;
- рабочие формы;
- клиентский пакет;
- FAQ и глоссарий;
- коммерческая упаковка;
- каталог и 12 кейсов.

Главный риск текущей версии не в отсутствии материалов, а в размере и управляемости комплекта. Пользователь может потеряться между файлами, версиями, внутренними документами, клиентскими документами, таблицами и кейсами.

Следующая версия должна не расширять теорию, а превратить комплект в управляемый релиз v0.4.

## 2. Принцип v0.4

v0.4 должна быть версией упрощения, синхронизации и внедрения.

Не нужно писать новые главы ради объема. Нужно:

- выровнять версии;
- зафиксировать главный источник правды;
- связать кейсы с продажей;
- усилить внедренческий слой;
- убрать дубли и устаревшие статусы;
- сделать комплект удобным для применения, а не только для хранения.

## 3. P1. Обязательные улучшения

### 3.1. Свести версии

Сейчас в папке документации одновременно живут v0.2 и v0.3.

Для v0.4 нужно создать единый релизный реестр:

- актуальные файлы;
- внутренние файлы;
- клиентские файлы;
- коммерческие файлы;
- файлы, которые уходят в архив;
- файлы, которые остаются только как технические заготовки.

Отдельная проблема: реестр структуры должен быть обновлен. В одном из реестров папка 50 Кейсы еще указана как пустая, хотя фактически уже есть каталог и 12 кейсов.

### 3.2. Собрать один главный документ-источник

Нужен главный документ:

`proSTRANSTVO_Operating_System_v0.4`

Он должен быть единственным источником правды по технологии.

В нем должны быть собраны:

- что такое проSTRAнство;
- логика технологии;
- этапы Диагностика -> Сессия -> Спринт -> Сопровождение;
- Problem Unit / проблемная единица;
- Наборы S/O/X;
- Триггеры T1-T14;
- ядро 115 инструментов;
- роли;
- вердикты Идти дальше / Go, Пауза / Hold, Остановить / Stop;
- артефакты каждого этапа;
- правила выбора моделей и инструментов;
- границы технологии;
- стоп-линии.

### 3.3. Связать кейсы с продажей

Сейчас кейсы существуют как доказательная база, но их нужно связать с коммерческой логикой.

Нужен мост:

`боль клиента -> похожий кейс -> триггеры -> продукт -> Диагностика -> данные -> следующий шаг`

Для этого требуется отдельный навигатор:

- какой кейс показывать клиенту;
- по какой боли;
- по какой функции;
- по какому триггеру;
- какой продукт предлагать после обсуждения кейса.

### 3.4. Усилить внедренческий слой

В v0.4 нужна не новая теория, а операционная книга внедрения.

Она должна описывать:

- ритм встреч;
- журнал решений;
- владельцев;
- метрики;
- контроль 30 / 60 / 90;
- еженедельный разбор;
- стоп-линии;
- формат фиксации отката;
- критерии завершения Спринта;
- критерии перехода в Сопровождение.

## 4. P2. Важные улучшения

### 4.1. Убрать дубли между документами

Нужно проверить и развести:

- FAQ;
- Glossary;
- Technology Guide;
- Operating System;
- Client Package Guide;
- Client Package Status;
- Project Start;
- Diagnostics;
- Session;
- Sprint;
- Support.

Цель: одно определение должно иметь один главный источник, а остальные документы должны ссылаться на него или давать прикладную версию.

### 4.2. Сделать Qualification Playbook / протокол квалификации

Нужен отдельный документ для первой продажи и входа в проект.

Он должен отвечать:

- кому подходит технология;
- кому не подходит;
- какие вопросы задавать до Диагностики;
- когда продавать стандартную Диагностику;
- когда продавать расширенную Диагностику;
- когда сразу ставить Пауза / Hold;
- когда сразу ставить Остановить / Stop;
- какие данные запросить до старта.

### 4.3. Добавить матрицу доказательности

Нужно связать каждый этап с проверяемым результатом.

Формат:

| Этап | Артефакт | Чем подтверждается | Кто принимает |
|---|---|---|---|
| Диагностика | карта текущего контура | данные, интервью, проблемная единица | спонсор проекта |
| Сессия | рабочий набор и мост | выбранные модели, инструменты, владельцы | первый управленческий круг |
| Спринт | контур 30 / 60 / 90 | метрики до / после, журнал решений | владелец Спринта |
| Сопровождение | устойчивость контура | ритм, откат, корректировки | спонсор и владелец контура |

### 4.4. Уточнить статус pack-документов v0.2

Короткие документы:

- Diagnostic Pack v0.2;
- Session Pack v0.2;
- Sprint 30-60-90 Pack v0.2;
- Support Pack v0.2;

нужно либо обновить до v0.4, либо явно обозначить как внутренние технические заготовки.

## 5. P3. Полезные улучшения

### 5.1. Сделать Case Selector / навигатор кейсов

Нужен короткий документ на 1-2 страницы:

- номер кейса;
- отрасль;
- основная боль;
- триггеры;
- функции;
- статус;
- какой первый вопрос задать клиенту;
- какой продукт предлагать.

### 5.2. Сделать changelog v0.4

Нужен журнал изменений:

- что изменилось;
- что исправлено;
- что перенесено;
- что ушло в архив;
- какие правила контроля добавлены.

### 5.3. Упростить публичный язык

Для публичных и коммерческих материалов нужно меньше внутренних терминов.

Принцип:

- внутри методологии можно использовать Problem Unit / проблемная единица, Bridge / мост, Gate / шлюз;
- в клиентской подаче сначала говорить простым языком: боль, разрыв, данные, решение, владельцы, результат;
- служебные термины давать только там, где они помогают управлению проектом.

### 5.4. Подготовить шаблон коммерческого предложения

Документ по продуктам, срокам и ценам уже создан.

Следующий коммерческий шаг:

- шаблон КП;
- структура первого письма;
- структура предложения после Диагностики;
- вариант предложения на полный цикл;
- вариант предложения на Сопровождение.

## 6. Рекомендуемый порядок работы над v0.4

1. Обновить единый реестр комплекта v0.4.
2. Зафиксировать статус каждого файла: актуален, обновить, архив, внутренний, клиентский, коммерческий.
3. Собрать главный Operating System v0.4.
4. Сделать Case Selector / навигатор кейсов.
5. Сделать Qualification Playbook / протокол квалификации.
6. Усилить внедренческий слой: Спринт + Сопровождение как операционный контур.
7. Сделать матрицу доказательности.
8. Обновить клиентский пакет только после обновления ядра.
9. Сделать changelog v0.4.
10. После этого готовить КП, презентацию и сайт.

## 7. Что не делать в v0.4

Не рекомендуется:

- писать новые главы без необходимости;
- добавлять новые инструменты без пересмотра ядра;
- расширять кейсы до отдельной книги;
- переписывать все документы одновременно;
- смешивать внутренний методологический язык и клиентский язык;
- верстать документы до содержательного согласования;
- выпускать v0.4 без единого реестра и changelog.

## 8. Главный критерий готовности v0.4

v0.4 готова, если внешний или внутренний пользователь может за 10 минут понять:

- что такое проSTRAнство;
- кому технология подходит;
- с чего начинается проект;
- какие этапы есть;
- какой результат на каждом этапе;
- какие документы использовать;
- какой кейс показать клиенту;
- какой продукт продавать;
- где технология должна сказать Пауза / Hold или Остановить / Stop.

Итоговая цель v0.4: не увеличить комплект, а сделать его управляемым, продаваемым и внедряемым.
